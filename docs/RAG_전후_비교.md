# RAG 사용 전후 품질 비교

같은 질문을 **RAG 없이 한 번, RAG(근거 검색 + 프롬프트 3)로 한 번** 답하게 하고, 세 기준으로 비교했다.
- 사실 정확성
- 근거 제시 여부
- 모르는 것을 모른다고 답하는지

답변 원문과 RAG가 인용한 근거 원문은 `python -m evaluation.rag_compare`를 실행하면 `docs/RAG_전후_비교_실행결과.md`로 생성된다(매뉴얼 원문 인용이 있어 저장소에는 넣지 않음).

## 1. 비교 조건

| 항목 | RAG 없이 | RAG |
|---|---|---|
| 모델 | gpt-4o-mini, temperature 0 | 같음 |
| 역할 | "자동차 정비 안내 전문가 … 한국어로 답합니다" | 같은 역할 + 프롬프트 3 규칙(근거만 사용, [n] 표시, 없으면 "확인되지 않음") |
| 입력 | 질문 (+ 내 차) | 질문 (+ 내 차) + 검색된 근거 (신호 메타데이터·매뉴얼·리콜) |
| 질문 | 9개. 근거 없이 답하면 틀리기 쉬운 질문 8개 + 수집 문서에 없는 질문 1개 | 같음 |
| 측정 시점 | 2026-10-22 오전~정오. 팰리세이드 매뉴얼을 추가하기 전 색인(매뉴얼 5권) | 같음 |

**판정 기준.** 사실 정확성은 **수집한 공식 근거**(현대·기아 매뉴얼, 공공 리콜 데이터)와 대조했다. 일반적으로 알려진 내용이라도 근거 문서에 없으면 '근거 없음'으로 본다. 위험 도메인이라 출처를 댈 수 있는지가 중요하기 때문이다.

| 표시 | 뜻 |
|---|---|
| ✅ | 근거와 일치 |
| △ | 핵심 일부 누락이나 근거 없는 단정 포함 |
| ❌ | 근거와 반대이거나 핵심이 틀림 |
| ➖ | 수집 근거 밖이라 판정 불가 |

판정은 실행 결과를 사람이 읽고 근거 원문과 대조해 정리했다.

## 2. 질문별 비교

| # | 질문 | 근거(매뉴얼·리콜)가 말하는 것 | RAG 없이 | RAG |
|---|---|---|---|---|
| 1 | 엔진 경고등 켜짐 vs 깜빡임, 계속 달려도 되나? | 3초 뒤에도 켜져 있으면 엔진 제어·연료 공급 장치 이상 → 가능한 한 빨리 점검. "켜지거나 깜빡이는 상태로 계속 주행하면 배기 제어 계통 손상". **둘의 차이는 말하지 않음** | △ "깜빡이면 즉시 차를 멈춰야" — 수집한 매뉴얼에 없는 단정. "상황에 따라 계속 주행 가능"도 근거 없음 | △ 대처(계속 주행 시 손상, 점검)는 근거대로 [2]. 그러나 "같은 상태가 아닙니다"는 근거에 없는 단정 — 이 부분은 "확인되지 않음"이라고 했어야 함 |

| 5 | 연료 캡을 덜 잠가도 엔진 경고등? | 켜질 수 있음, 고장 아님, '딸깍' 소리 나게 다시 잠그고 안 꺼지면 점검 | ✅ 핵심은 맞음. 다만 원인 설명(O2 센서 등)은 근거에 없는 내용 | ✅ 근거대로, "고장 아님"까지 [2] |
| 6 | '변속기 과열! 시동을 켠 채로 정차하십시오' — 시동을 끄는 게 낫지 않나? | 안전한 곳으로 이동 → **P단, 시동을 켠 채로 정차** → 충분히 냉각될 때까지 대기 | ❌ **"시동을 끄는 것이 좋습니다"** — 매뉴얼 지시와 정반대 | ✅ "시동을 끄지 않고 정차", P단·냉각 대기 [2, 3] |

## 4. 해석

- **RAG의 가장 큰 효과는 "상식과 매뉴얼이 다른 곳"에서 나왔다.**
  - RAG 없이는 "과열이면 시동을 끈다", "깜빡이면 공기 부족" 같은 그럴듯한 상식으로 답했고, 그 결과 매뉴얼 지시와 정반대로 안내했다(#3, #6).
  - 경고등 안내에서는 이런 오류가 곧 안전 문제다. RAG는 두 경우 모두 매뉴얼 지시를 그대로 전달했다.
- **근거가 있어야만 답할 수 있는 질문(리콜 #8)에서는 RAG만 실제 정보를 줬다.**
  - RAG 없이는 정직하게 모른다고 했지만 용어(ICCU)를 잘못 풀이했다.
- **RAG도 근거에 없는 단정을 완전히 막지는 못했다.** 세 건이 남았다.
  - "켜짐과 깜빡임은 다르다"(#1)
  - 메타데이터를 인용하며 "정차·점검" 권고(#7)
  - "리콜 대상입니다"(#8)

  공통점이 있다. **질문이 기대하는 결론을 LLM이 채워 넣은 경우**다. 근거 번호가 붙어 있어 사용자가 원문과 대조할 수 있다는 점이 RAG 없는 답과의 차이다.
- **모르는 것은 모른다고 하는 대신, 답이 짧아진다.**
  - 와이퍼(#9)처럼 근거 밖 질문에는 도움이 되는 일반 정보도 주지 않는다.
  - 위험 도메인에서 출처 없는 답을 피하려고 일부러 택한 동작이다.

## 6. 프롬프트 개선 후 다시 비교

5장의 개선안을 적용한 뒤 **같은 9문항의 RAG 답을 질문마다 2번씩** 다시 받았다. LLM 답은 실행마다 흔들려서, 한 번 결과로 개선을 단정하지 않기 위해서다. 원문은 `docs/RAG_프롬프트개선_실행결과.md`(`python -m evaluation.rag_compare --rag-only --runs 2 --out docs/RAG_프롬프트개선_실행결과.md`로 생성)에 있다(`python -m evaluation.rag_compare --rag-only --runs 2`).

| # | 개선 전 (1회) | 개선 후 실행 1 | 개선 후 실행 2 |
|---|---|---|---|
| 1 엔진 켜짐/깜빡임 | △ 차이 단정 | ✅ 차이는 "확인되지 않음", 계속 주행 시 손상 [2] | ✅ 같음 |
| 2 브레이크 + ABS | ✅ | ✅ | ✅ |
| 3 TPMS | △ '공기압 저하' 빠짐 | △ **새 부작용**: 차이를 맞게 설명한 뒤 "차이는 확인되지 않음"을 덧붙여 자기모순 | ✅ 깜빡임 후 점등 = 시스템 이상 / 바로 켜짐 = 공기압 저하 |
| 4 거북이 | ✅ | ✅ (+ 급가속·급출발 금지) | ✅ |
| 5 연료 캡 | ✅ | ✅ | ✅ |
| 6 변속기 과열 | ✅ | ✅ | ✅ |
| 7 핸들 빨간 그림 | △ 메타데이터 인용해 "정차·점검" | △ 인용 오용은 사라짐. 그러나 핸즈오프로 단정하고 다른 후보를 밝히지 않음 | △ 같음 |
| 8 ICCU 리콜 | △ "리콜 대상입니다" | △ "내 차에 리콜이 있었던 것으로 확인됩니다"(완화됐지만 경계선) | ✅ "이 차종에 리콜 기록이 있으니 차대번호로 확인" |
| 9 와이퍼 | ✅ 확인되지 않음 | ✅ | ✅ |
| **사실 정확성 합계** | ✅4 △4 ❌0 (+모름 1) | ✅5 △3 ❌0 (+모름 1) | ✅7 △1 ❌0 (+모름 1) |

**결과**
- 개선 전에 남았던 근거 없는 단정 3건이 이렇게 바뀌었다.
  - #1 차이 단정: 2회 모두 해결
  - #7 메타데이터 인용 오용: 2회 모두 해결
  - #8 리콜 대상 단정: 1회 해결, 1회 완화
- **LLM은 "후보가 여럿이면 각각 밝혀라" 규칙을 두 번 다 따르지 않았다(#7).** 핸들 그림 질문은 전동 파워 스티어링 경고등일 수도 있고, 그 경우라면 점검이 필요하다. 이건 안전과 관련된 문제라 LLM에 맡기지 않았다. 화면이 retrieve가 찾은 후보 신호를 답변 아래에 **"설명에 맞을 수 있는 신호 — 내 계기판과 같은지 확인해 보세요"**로 항상 보여 주고, 누르면 그 신호의 진단 카드로 간다([캡처](images/candidate-signals.png)).
- 이와 함께, 인용한 근거가 없는 답(와이퍼처럼 "확인되지 않음")에는 후보 신호와 리콜을 붙이지 않게 했다. 근거가 없을 때도 검색은 신호를 억지로 고르는데, 개선 전에는 그 신호를 기준으로 ICCU 리콜까지 붙었다.
- **새 규칙의 부작용이 나왔다.**
  - #3 실행 1에서 비교 규칙을 과하게 적용해 자기모순이 생겼다.
  - 회귀 시나리오(`evaluation.qa_scenarios`)의 이어지는 질문 "그럼 브레이크액은 어떻게 보충해?"가 한 번은 "확인되지 않음"으로만 답했다. 같은 질문을 두 번 더 돌리자 두 번 모두 "보충 방법은 확인되지 않음 + 부족하면 즉시 보충 [n] + 보충 후에도 켜지면 점검 [n]"으로 바람직하게 답했다. 그래서 일관된 회귀가 아니라 3번 중 1번 생기는 흔들림으로 판단하고 규칙은 더 바꾸지 않았다.
- 진단 카드 긴급도(TPMS 빠른 점검, 변속기 과열 즉시 정차, 후측방·핸들 즉시 조치)는 개선 뒤에도 기대 범위 안이었다.

## 7. 참고: 응답 시간

실행결과 표의 시간에는 이번 측정 때 있었던 **LLM API 서버 응답 지연**이 섞여 있다. 같은 클라이언트로 "한 단어로: 안녕"만 보내도 1초 안팎이다가 13~18초로 튀는 경우가 있었다. 그래서 RAG 6.5~34초, RAG 없이 2.3~15.5초로 편차가 컸다.

측정하다 서비스 코드의 지연 원인도 하나 찾았다.
- LLM·임베딩 클라이언트와 벡터 저장소를 호출할 때마다 새로 만들고 있었다.
- 그래서 매번 연결을 다시 맺느라 임베딩 1회에 약 5초가 걸렸다.
- 한 번 만든 객체를 재사용하도록 고친 뒤(`src/llm.py`, `src/vectorstore/`) 임베딩은 1회 0.4~0.9초가 됐다.
- API 지연이 없을 때 다시 잰 전체 처리 시간은 질문 답변 4.1초, 진단 카드 4.6초였다.
